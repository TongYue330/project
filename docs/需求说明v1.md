（3）核心价值概括
一句话概括：让大学生遇到不会的作业题时，拍一张照片就能获得分步骤的详细解答，同时通过人工确认和纠错机制避免被AI的错误答案误导。

用户使用前后的可观察变化：

使用前：遇到不会的题 → 手动打字搜索或群里求助 → 等待长时间回复或得到不完整答案 → 卡住甚至放弃。

使用后：拍照上传题目 → 几秒内获得分步骤解答 → 对照解答理解解题思路 → 如有疑问可标记“这步没看懂”进一步追问。

（2）本项目不准备解决的问题
不做完整的课程学习平台，不包含课程视频、教材讲解等功能。

不做作业批改，不判断学生答案的对错，只负责解答学生提出的问题。

不做错题本和练习册生成，专注“答疑”这一核心场景。

不做社交功能，不与同学、老师互动。

（3）借鉴与差异
可以借鉴的设计：

豆包的“分步骤讲解+多模态图文说明”方式值得学习，解答不仅要给结果，还要展示过程。

千问的“围绕同一知识点连续提问”思路可以借鉴，用于实现学生对某一步骤的追问。

仍未解决的问题：

现有工具的AI答案错误率依然存在。公开学术研究显示，在RAG增强的AI辅导系统中，每门课约2%~4%的查询无法正确应答。来源：公开学术研究，具体文献可自行补充。

大厂产品面向全年龄段，功能繁杂，大学生使用时需要从大量非学习功能中找到答疑入口。

现有工具缺少让学生主动标记“疑似错误”的机制，学生遇到错误答案后只能自己判断，无法反馈。

本项目的差异：专注大学生作业答疑场景，轻量级、入口简单，同时通过“人工确认”和“错误反馈”机制来缓解AI答案不可靠的问题。

2.5 AI能力必要性与可行性
（1）为什么难以用固定规则解决
作业题目的表述方式千变万化，同一道数学题可以用不同的符号、格式、语言来描述。传统规则系统需要为每种题型预先编写匹配模板，维护成本极高且覆盖面有限。大模型能够理解自然语言的题目描述，并生成分步骤的解题过程，这是规则系统做不到的。

（2）AI能力设计
表2-10 AI能力设计表

项目	内容
模型输入	题目图片（base64编码）或题目文字
期望输出	分步骤解答，包含每步的公式/代码和文字解释
允许错误	允许AI在复杂题目上出错，但需明确标注“AI生成，仅供参考”
人工确认点	AI置信度低于阈值时自动提示用户核实；用户可主动标记“疑似错误”

费用	按Token计费，新用户有免费额度，个人开发成本可控
时延	目标≤15秒（含图片上传+模型推理+结果返回）
隐私	题目图片和文字仅用于本次解答，不存储到服务器
幻觉风险	AI可能给出错误答案，通过置信度提示和用户反馈机制缓解
评测难点	缺乏标准化的题目-答案数据集，需要人工抽样评估解答质量

过程记录（2.1—2.5）
2.1 过程记录
调研过程：我先在班级群里连续观察了两周，发现平均每天有3到5条题目求助，回复率不到一半。之后查阅了中国青年报关于大学生AI使用情况的调查，了解到57.07%的受访者遇到过AI答案错误的问题。又浏览了36氪关于AI教育赛道的分析，发现豆包和千问在2026年3月升级了学习功能，但主要面向中小学生。

分析过程：结合个人经历和班级群观察，确认大学生课后作业答疑是一个真实且未被充分满足的需求。大厂产品功能繁杂，面向全年龄段，大学生使用时入口较深，且缺少对AI答案的纠错机制。

需求变化：最初设想的选题比较宽泛，后来聚焦到“拍照上传题目+AI分步骤解答+人工确认”这一条核心链路，把范围收窄到大学生作业答疑。

2.2 过程记录
调研过程：主要来自个人经历和身边同学的反馈，同时参考了班级群里的求助记录。没有做正式访谈，但和几位同学交流过他们做作业时遇到的困难。

分析过程：根据这些信息总结出主要用户是在校大学生，特别是理工科和计算机相关专业。典型场景的设计参考了实际作业答疑流程：拍照上传、获取解答、针对某步追问、查看历史记录。最初只考虑了正常场景，后来在分析AI可能出错的情况时，补充了图片模糊无法识别和AI答案可能有误这两个异常场景。

取舍：次要用户最初考虑过“家长”角色，但大学生场景中家长参与度低，最终只保留助教/教师作为次要用户。

2.3 过程记录
调研过程：下载并试用了豆包和千问的拍题答疑功能，记录了功能入口、操作流程和响应速度。选择这两款是因为它们在应用商店下载量最高且都免费。还查阅了官网和帮助文档，并在GitHub上搜索过开源拍题项目，但大多功能不完整。

调研过程：参考了敏捷开发中用户故事和验收条件的常见写法，没有做外部调研，主要基于项目自身需求。

分析过程：先列出学生使用软件的主要步骤，然后按“作为……我希望……以便……”格式写初稿。后来考虑到实际使用中可能出现的问题，补充了图片识别失败和AI答案不确定这两种情况的用户故事。验收示例参考了Given/When/Then格式，覆盖正常、信息不足、失败和需要人工确认四类情况。用例图用PlantUML在线工具绘制。

需求变化：最初只写了4个用户故事，后来发现图片识别失败的情况也需要考虑，补充了US6。非功能需求也从最初只考虑性能，扩展到可靠性、安全和可用性。

2.5 过程记录
调研过程：测试了通义千问的qwen-vl多模态模型，也测试了本地模型Ollama在图片识别上的表现。

分析过程：作业题目表述千变万化，规则系统无法穷举。本地模型在图片识别上准确率明显低于云端模型，推理速度也慢。最终决定使用阿里云百炼平台API，新用户有免费额度，个人开发成本可控。隐私方面，题目数据仅用于本次解答，不长期存储。对于AI可能出错的问题，设计了置信度提示和用户反馈机制。

取舍：最初考虑过完全用本地模型以避免API费用，但测试后放弃。也考虑过用纯规则匹配题库，但发现覆盖面太窄，最终确定用大模型。

需求变化：在参考学术研究后，发现AI辅导系统的幻觉问题普遍存在，因此在需求中增加了“AI不确定时给出提示”和“用户可反馈错误”两个功能。
